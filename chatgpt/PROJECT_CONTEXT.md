# Project Context

## User

Name: Mücahit

Professional background:

- Approximately 5–6 years of software-development experience.
- Most professional work has been back-office applications built with React and Vue.
- Strong TypeScript and JavaScript knowledge.
- Has had learning-oriented experience with Go and C#, but does not consider that experience current.
- Currently works as a React Lead.

## Motivation

Mücahit has wanted to learn low-level programming for a long time and wants to do it through game development.

He has played many games and wants game design/mechanics to be the source of programming problems rather than following a traditional systems-programming syllabus disconnected from actual projects.

He is currently especially interested in:

- Odin
- Jai, but Jai is not publicly available enough for the learning path, so Odin is the practical focus

He already knows basic Odin syntax and does not want beginner syntax lessons.

## Desired experience

The initial analogy was **Boot.dev**, but not because the user wants a literal clone.

What he liked about Boot.dev was the workflow:

1. Read a lesson on a website.
2. Switch to a real code editor.
3. Implement the assignment himself.
4. Return for the next instruction/challenge.

After discussing a local website, the user said he prefers **this chat** as the mentor/lesson experience, so building an academy UI is not currently necessary.

A Codex CLI workflow was also discussed because it can inspect the local repository, run commands, review code, and see build/test output. The preferred separation is:

- Chat: curriculum, explanation, architecture, mentoring, lesson/challenge assignment
- Codex CLI: local repo inspection, build/run/test, code review, profiling/debugging assistance

## Core learning objective

The objective is not simply to make games.

The goal is to become capable of reasoning about and building the systems beneath games:

- game loops
- memory management
- allocators
- data layout
- cache behavior
- rendering
- physics/collision
- gameplay architecture
- serialization
- asset systems
- simulation
- replay/rewind
- networking
- tooling
- profiling
- debugging
- editor development
- game feel

## Core educational principle

> **Engine yaparak oyun öğrenmeyeceğiz. Oyun yaparak engine öğreneceğiz.**

No giant engine scaffold at the start.

Systems are extracted only after they are repeatedly needed by actual games.

## Intended mentor/student relationship over time

Beginning:

- Mentor provides concepts, constrained challenges, and acceptance criteria.
- User implements.
- Mentor reviews.

Middle:

- User designs APIs and architecture.
- Mentor asks questions and reviews tradeoffs.

Later:

- User behaves like an engine programmer.
- Mentor behaves more like a staff/principal engineer reviewer.
